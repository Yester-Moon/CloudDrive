## 一、项目概述

CloudDrive 是一个基于 .NET 8 / C# 12.0 的云存储网盘系统，采用 DDD 分层架构。

**技术栈**：

| 层 | 技术 |
|---|---|
| 表现层 | ASP.NET Core WebAPI, Swagger, JWT |
| 应用层 | Application Services, FluentValidation, CQRS (Command/Query 模型) |
| 领域层 | DDD 聚合根 / 实体 / 值对象 / 领域事件 (MediatR) |
| 基础设施层 | EF Core + SQL Server, ASP.NET Core Identity, 本地/OSS 存储 |
| 公共层 | JWT 组件, 缓存, 工具类, 异常体系, 验证规则 |

**架构**：

```
CloudDrive.sln
├── CloudDrive.Domain          # 领域层 — 实体、值对象、领域事件、仓储接口、存储接口
├── CloudDrive.Application     # 应用层 — 服务实现、DTO、Command/Query、验证器
├── CloudDrive.Infrastructure  # 基础设施层 — EF Core、仓储实现、存储实现、事件处理器、外部服务
├── CloudDrive.WebApi          # 表现层 — 控制器、中间件、统一响应、Program 启动
└── CloudDrive.Common          # 公共层 — JWT、缓存、DDD 基类、工具类、异常、常量、通用验证
```

## 六、技术债务

| 编号 | 技术债务 | 影响 | 优先级 |
|------|---------|------|--------|
| TD-1 | `FileService` / `ShareService` / `UserService` 使用 `InvalidOperationException` 而非 `BusinessException` 子类 | 异常处理不够精确，前端无法区分错误码 | P1 |
| TD-2 | `CommonValidationRules` 已定义但未绑定到 Command 验证管道 | 请求参数未经过 FluentValidation 验证 | P0 |
| TD-3 | Request Model 定义在 Controller 文件内（内联） | 文件过长，不利于维护和复用 | P1 |
| TD-4 | `OssStorageProvider` 核心方法为 `NotImplementedException` | OSS 存储不可用 | P2 |
| TD-5 | `EmailService.SendAsync` 为日志占位 | 邮件通知不可用 | P0 |
| TD-6 | `NotificationService` 仅日志记录 | 用户无法收到实际通知 | P2 |
| TD-7 | `ShareLink.GenerateShareCode()` 使用 `new Random()` 而非 `Random.Shared` | 并发场景下可能生成重复分享码 | P1 |
| TD-8 | 无单元测试和集成测试 | 质量无保障，重构风险高 | P0 |
| TD-9 | 仓储每次操作调用 `SaveChangesAsync` 而非统一由 UnitOfWork 控制 | 复合操作无法原子提交 | P1 |

## 八、总结

项目从上次评估的 **约 25%** 已推进到 **约 75%**。核心业务链路（注册→登录→上传→下载→分享→配额管理）的代码已完整，DDD 模式执行到位。

**当前关键短板**：

1. **零测试覆盖** — 最大风险
2. **验证管道未落地** — 请求参数可绕过校验
3. **异常体系未统一使用** — 已定义 `BusinessException` 但服务层仍抛通用异常
4. **仓储未统一事务** — 复合操作缺少原子性

完成 P0 事项后即可达到 **MVP 可部署状态**，预计 **2-3 周**。
